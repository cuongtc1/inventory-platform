## Goal

The second backend service: users with hashed passwords and a login that hands out a signed token, so the gateway (T3.3) and the role rules (T3.4) have something to check.

## Your decisions

| Question | Choice |
|---|---|
| JWT library | Spring Security's own (`spring-security-oauth2-jose`, Nimbus inside), so the gateway can check tokens with Spring Security's resource-server support |
| Token lifetime | 8 hours (`JWT_EXPIRATION`), no refresh token |
| First admin | Created at startup from `ADMIN_EMAIL` / `ADMIN_PASSWORD` when the users table is empty; nothing committed in a migration |

## What we did, step by step

### 1. New service from the product-service template
- Same pom (Boot 4.1.1, springdoc 3, stockline-common, Testcontainers, Mockito agent), wrapper, `.gitattributes`, `application.yml` layout, port 8081, schema `auth_db`.
- Only two Spring Security modules, not the full starter: `spring-security-crypto` (BCrypt) and `spring-security-oauth2-jose` (`JwtEncoder`). Login needs no security filter yet.

### 2. Database
- `V1__create_users.sql`: `email` (unique, lower case), `password_hash` (BCrypt), `full_name`, `user_type` (STAFF / MANAGER / ADMIN), `status` (ACTIVE / INACTIVE), audit columns.
- `status` as a string enum like `products.status`, not a BOOLEAN: MySQL stores BOOLEAN as TINYINT, which Hibernate's schema validation reads as a mismatch for `boolean`.

### 3. Login
- `AuthService.login`: email trimmed and lower-cased; password checked with BCrypt; unknown email, wrong password and deactivated user all throw the same `UnauthorizedException` ("Wrong email or password").
- An unknown email is still checked against a dummy hash, so the response time doesn't reveal which emails exist.
- `TokenService`: HS256 token with `iss`, `sub` (user id), `email`, `name`, `role`, `iat`, `exp`; times from the `Clock` bean.
- `LoginResponse`: `accessToken`, `tokenType` "Bearer", `expiresAt`, `user { id, email, fullName, userType }`.

### 4. Configuration
- `JwtProperties` and `AdminProperties` as `@ConfigurationProperties` records with `@Validated`; `JWT_SECRET` shorter than 32 bytes stops the startup.
- `AdminAccountInitializer` (`ApplicationRunner`): creates the ADMIN only on an empty table, logs the email, never the password.

### 5. Shared library
- `UnauthorizedException` (401) and `JwtClaimNames` (`email`, `name`, `role`), because the gateway and the services will read the same claims.

### 6. Docker and docs
- Dockerfile and compose entry (`JWT_SECRET`, `JWT_EXPIRATION`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` in `.env.example`); image built and started once, login checked against the container.
- auth-service README, conventions section 11 "Authentication and JWT", CLAUDE.md commands, infra README.

## Problems we hit and how we fixed them

| Problem | Fix |
|---|---|
| `mvnw install` of the library: "Failed to install artifact ... .tmp -> ... .jar" | Windows can't replace a jar another program has open; Spring Tools held it. You closed Spring Tools; the tip is now in the library README |
| `MessagesPropertiesTest` copied from product-service required at least one custom validation key | `LoginRequest` uses only standard texts; the check now allows none |
| `jwtEncoder` bean method was package-private, the test in another package couldn't call it | Made it public |
| Stopping the local run left the forked JVM on port 8081, so the container couldn't start | Stopped the remaining processes, then started the container |
| `mvnw` committed without the executable bit (copied on Windows) | `git update-index --chmod=+x`, separate commit |

## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now |
|---|---|
| jjwt `Jwts.builder()...signWith(key)` | Spring Security `JwtClaimsSet.builder()` + `JwtEncoder.encode(...)`, `NimbusJwtEncoder.withSecretKey(key).algorithm(HS256)` |
| `@ConfigurationProperties` class with setters + `@EnableConfigurationProperties` | A `record` with a compact constructor + `@ConfigurationPropertiesScan` |
| `CommandLineRunner` | `ApplicationRunner` (parsed arguments) |
| Login by checking the password and returning `"OK"` + a session | Stateless JWT: the token itself proves who you are until `exp` |

## Concepts explained during this task

- **JWT:** header, claims and signature, Base64 and dot-separated. Readable by anyone, but changing a claim breaks the signature (`TokenServiceTest` forges STAFF → ADMIN and is rejected).
- **BCrypt:** slow, salted hash; the same password gives a different hash each time, `matches` still works. Only the first 72 bytes count, hence the 72-character limit.
- **Same answer for every login failure**, and the dummy-hash check against timing attacks.
