## Goal

The fourth domain service: running, secured and with its tables, ready for customers, sales orders and the state machine.

## What we did, step by step

### 1. Service from the template
Pom, wrapper, `application.yml` (port 8084, `order_db`), Dockerfile, compose entry, `.env.example`. Security from the start: `WebSecurityConfig` with reading for STAFF and changing for MANAGER, a starting rule for T5.2 and T5.3 to refine. The gateway already had the routes. `RestClient` stays out until T5.3 uses it.

### 2. Migrations, one per table
- `customers`: unique `name`, optional `email` and `phone`.
- `sales_orders`: unique `order_number`, `customer_id` with a foreign key, `warehouse_id` and `warehouse_code`, `status`, `total_amount`, `version`.
- `sales_order_items`: copies of SKU, name and price, one line per product, CHECK on `quantity` and `unit_price`.
- `order_status_history`: `from_status`, `to_status`, `note`; never updated or deleted.

### 3. Choices beyond the task text
- `warehouse_id` and `warehouse_code`: the mockup's order form picks a warehouse, and the saga reserves stock there.
- `total_amount` is stored because the list sorts by it; line totals are calculated.
- `note` on the history: why a rejected order was rejected.
- `outbox_events` and `processed_events` wait for the Phase 6 tasks that use them.

### 4. Tests
`MigrationsTest` with plain SQL (no entities yet), `SecurityRulesTest`, `OrderServiceApplicationTests`: 21 tests.

## Concepts explained during this task

- **Snapshots:** an order keeps the name and price of that moment, so a later rename or price change doesn't rewrite it.
- **Stored or calculated:** calculate by default, so numbers can't disagree. Store only when a query needs it, as with `total_amount` for sorting, and only if the source can't change afterwards.
- **`version` on orders:** a user and a Kafka event can change the status at the same moment.
