## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now (Boot 4 / Java 21) |
|---|---|
| Repository queries always built at startup through proxies | Spring Data 4 can also generate them **ahead of time** as Java source (`*Impl__AotRepository.java`) during an AOT build |
| `javax.validation.constraints.Email` | `jakarta.validation.constraints.Email` |
| `str.trim()` | `str.strip()` (Java 11) also removes Unicode whitespace; `isBlank()` (Java 11) checks for whitespace only |

## Concepts explained during this task

- **AOT repositories (Spring Data 4):** at build time (`process-aot`), Spring Data reads repository method names and writes the query code as real classes in `target/spring-aot/main/sources`. They are used only when AOT is on: a GraalVM native image, or `-Dspring.aot.enabled=true`. Normal `spring-boot:run`, `java -jar` and tests still derive queries at startup, so a stale or empty AOT file doesn't break anything. Never edit or commit them (they're in `target/`). Only custom methods appear; `findById`, `save` and the rest come from `SimpleJpaRepository`. You can open them to see the JPQL generated from a method name.
- **PUT replaces everything:** a field missing from the body becomes `null`. That's why the update test sends no phone and expects it cleared.
- **Null-friendly constraints:** `@Email`, `@Pattern` and `@Size` treat `null` as valid; only `@NotNull` / `@NotBlank` make a field required.
- **Unique key as the last line of defence:** the service checks `existsByName` first for a friendly 409, but two requests at the same moment can both pass the check. The database unique key still stops the second insert (handled properly in T1.6).
