## Goal

List, create, edit and delete categories and suppliers, the same way as products, and turn the product pages' code into shared pieces before it was copied a third time.

## What we did, step by step

### 1. API and routes
- `api/categories.ts`, `api/suppliers.ts`: `get`, `create`, `update`, `delete` added next to the list calls and the `get...Options` functions.
- Routes `/categories/new`, `/categories/:id/edit`, `/suppliers/new`, `/suppliers/:id/edit` (lazy pages).

### 2. Shared pieces pulled out of the product pages
| Piece | Replaces |
|---|---|
| `components/PagedTable` | the list card: filter row with Reset, error with "Try again", Table with backend paging/sorting |
| `components/SearchFilter` | the `Input.Search` with the `key` trick |
| `components/RecordFormPage` | reading `:id`, loading the record, spinner, "not found", "Page not found", Back button |
| `components/FormActions` | "Save changes" and "Cancel" |
| `components/AuditInfo` | the "Created … by …" line |
| `formFieldErrors(error, { DUPLICATE: 'name' })` | the per-page `if (code === 'DUPLICATE')` |
| `FORM_MAX_WIDTH` | the 960 written in each form |

`ProductListPage` and `ProductFormPage` were rewritten on top of them; the browser tests of T2.3 were run again with the same results.

### 3. Categories
- List: Name (link to edit), Parent, Products (count, links to `/products?categoryId=…`), Edit/Delete. Sort by name or `parent.name` (checked first through the API that top-level categories stay in the list: Spring Data uses an outer join). The count is computed per page, so it isn't sortable.
- Form: Name and Parent ("None (top level)"). The category itself isn't offered as parent; a loop (moving under a subcategory) comes back as `BAD_REQUEST` and is shown under Parent.

### 4. Suppliers
- List: Name, Contact, Email (`mailto:` link), Phone; all sortable.
- Form: Name required; email and phone checked in the browser (`PHONE_PATTERN` mirrors the backend); emptied fields are sent as `null`.

### 5. Checking (headless Edge, desktop and phone)
Search, sorting, count link, delete refused with `IN_USE` (category with products, supplier with products), empty and duplicate names, parent loop, create/edit/delete, invalid email and phone, clearing optional fields, unknown and invalid ids, no sideways scrolling on a phone.

## Problems we hit and how we fixed them

| Problem | Fix |
|---|---|
| The browser's own "Please include an '@'" popup covered our email message | `inputMode="email"` / `inputMode="tel"` instead of `type="email"` / `type="tel"`: same phone keyboard, no browser check |
| Test script couldn't clear a Select (the clear icon only exists while hovered) | Checked separately with real mouse events through the DevTools Protocol: clearing the parent saves "top level" |
| A shell script edit ran half-way and left wrong indentation | Fixed with the Edit tool; lint and build caught nothing else |

## New compared to Java 8/11 and Spring Boot 2.x

| Java / Spring | React / TypeScript |
|---|---|
| Template method / abstract base page | A component that takes the varying part as a function: `RecordFormPage` with `children(record, returnTo)` ("render prop") |
| `Map<ErrorCode, String>` | `Partial<Record<ErrorCode, keyof Values & string>>`: only real field names of the form are accepted |
| `ReturnType` has no Java equivalent | `type PagedList<T> = ReturnType<typeof usePagedList<T>>`: the type of what a generic function returns |

## Concepts explained during this task

- **Render props:** `RecordFormPage` does the loading and calls `children(record, returnTo)` to draw the form, so each page keeps only its own form.
- **`inputMode` vs `type`:** `inputMode` only chooses the phone keyboard; `type="email"` also turns on the browser's own validation.
