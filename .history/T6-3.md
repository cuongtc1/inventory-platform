## Goal

When two changes hit the same stock level at the same moment, never sell more than there is, and don't make the loser fail just because of the collision.

## What we did, step by step

### 1. Retry
`StockReserver.reserve` and `StockAdjuster.apply` got `@Retryable` (Spring Framework 7) on `ConcurrencyFailureException`: version conflicts and deadlocks. Settings in `StockRetry`: 5 retries, 20 ms doubling up to 500 ms, 10 ms jitter. `ResilienceConfig` switches it on with `@EnableResilientMethods`.

### 2. Retry outside, transaction inside
Both methods lost `@Transactional`; each attempt runs in `TransactionOperations.execute(...)`, a fresh transaction that re-reads the stock and checks the rules again. Unit tests pass `TransactionOperations.withoutTransaction()`.

### 3. Parallel consumers
`spring.kafka.listener.concurrency: 3` in inventory-service: one consumer thread per partition.

### 4. Tests
`StockConcurrencyTest`: threads released by a `CyclicBarrier` race on real MySQL (two orders for the last items, ten orders for five items with retries counted through `MethodRetryEvent`, ten adjustments at once).

## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now |
|---|---|
| Spring Retry (extra library), `@EnableRetry` | `@Retryable`, `@EnableResilientMethods` in spring-context (Spring Framework 7), `MethodRetryEvent` per retry |
| `@Transactional` on the method | `TransactionOperations.execute(status -> ...)` for one transaction per attempt |
| `shutdown()` and `awaitTermination()` | `try (ExecutorService pool = ...)` |

## Concepts explained during this task

- **Optimistic locking:** read without locking, write with `WHERE version = ?`; a stale write finds no row. Cheap when conflicts are rare.
- **Lost update:** two writers both read 0 and write 1; the version check turns the second write into an error.
- **Never oversold even without retry:** the version check alone refuses the stale write; the retry only turns the loser's error into a fair answer.
- **Jitter:** random extra wait, so colliding transactions don't retry in lockstep.
- **Consumer concurrency and ordering:** one thread per partition keeps each order's events (same key, same partition) in order.
