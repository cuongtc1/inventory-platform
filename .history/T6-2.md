## Goal

The first saga: an order gets its stock reserved by another service, and finds out over Kafka whether it worked.

## What we did, step by step

### 1. order-service
- `OrderCreatedEvent` (orderId, orderNumber, warehouseId, items with SKU and name), published by `OrderEventPublisher` after the order's transaction has committed, keyed by the order id, without making the HTTP request wait.
- `StockEventsListener`: `stock.reserved` → RESERVED, `stock.failed` → REJECTED with the reason as history note, through `OrderStatusService` (author `system`). An event for an order that is no longer PENDING, or doesn't exist, is logged and skipped.

### 2. inventory-service
- `StockReserver`: checks every line first, then for each line raises `reserved` (not `on_hand`), stores a `StockReservation` and a RESERVE movement with the order number as reference. All or nothing, in one transaction. A product never stocked counts as 0 available.
- `StockReserver.Result`: a sealed interface with the records `Reserved` and `Failed`.
- `OrderEventsListener`: reads `order.created`, reserves, sends `stock.reserved` or `stock.failed` after the commit.
- New: `StockReservation`, `ReservationStatus`, `StockReservationRepository`, `StockLevel.reserve`.

### 3. Tests
Kafka listeners are off in tests by default (`src/test/resources/config/application.yml`); `OrderSagaTest` and `StockReservationSagaTest` switch them on and each plays the other service. `StockReserverTest` and `StockEventsListenerTest` cover the rules without Kafka.

## Your decisions

None needed: TASKS.md, the conventions and the mockup decided the choices (all or nothing, RESERVE movements, publish after commit, skip events that no longer fit).

## Problems we hit and how we fixed them

| Problem | Fix |
|---|---|
| Real listeners in several cached test contexts would share the service's consumer group and answer events from the wrong database | Listeners off in tests by default; only the saga tests start them; the T6.1 listener test starts only its own listeners (`autoStartup = "true"`) |
| `OrderSagaTest` read another test's order: ids repeat across test databases, the broker is shared | The test positions its consumer at the end of the topic before creating the order |
| I wrote that a duplicate delivery is refused by the reservations' unique key, which wasn't tested | Reworded as an expectation; T6.4 tests it |

## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now |
|---|---|
| A result class with a type field, or an exception for "failed" | A `sealed interface` with record implementations (Java 17) |
| `instanceof` checks and casts | `switch` with record patterns (Java 21): `case Failed(long orderId, String reason) ->`, no `default` needed |
| Test config with profiles | `src/test/resources/config/application.yml`, loaded on top of the main `application.yml` |

## Concepts explained during this task

- **Saga:** a business transaction across services as a chain of local transactions and events, instead of one distributed transaction.
- **Publish after commit:** an event never describes something that was rolled back; the price is that a crash between commit and send loses it (the outbox fixes that).
- **Reserved vs on hand:** reserving promises stock without moving it; `available = on_hand - reserved`.
- **Consumer lag:** `kafka-consumer-groups.sh --describe` shows how far each group is behind; 0 means everything is processed.
