## Goal

See the history of stock: what changed, where, when and by whom.

## What we did, step by step

### 1. The list
`GET /api/stock-movements`, newest first, read-only, for STAFF and up. `StockMovementFilter` (a record bound from query parameters), `StockMovementSpecifications`, `StockMovementMapper`, `StockMovementService`, `StockMovementController`. The repository got `JpaSpecificationExecutor` and an entity graph, so the warehouse comes in the same query.

### 2. Filters
`warehouseId`, `productId`, `movementType`, `from`, `to`, and `search` (part of the product name or SKU, like the stock levels list; not in the task, added because it costs little). `from` and `to` are Vietnam dates, both included: `createdAt >= startOfDay(from)` and `createdAt < endOfDayExclusive(to)`.

### 3. Refusals
`from` after `to` gives `400 BAD_REQUEST` with the key `stock.movement.date-range`. A bad date or an unknown type gives `400 VALIDATION_FAILED` on that field. `POST` gives 405.

### 4. Shared code
`StockLevelSpecifications.containsPattern` (lower case and LIKE escaping) is used by both specifications, instead of a second copy.

## Problems we hit and how we fixed them

| Problem | Fix |
|---|---|
| 4 repository tests failed on the day boundary: rows were 7 hours late | My test wrote `created_at` with `java.sql.Timestamp`, which the driver converts to the JVM's zone (UTC+7 on this laptop). It now writes a `LocalDateTime`, stored as written. The service code was right |
| I blamed the wrong setting: I said `hibernate.jdbc.time_zone: UTC` keeps stored times in UTC | Tested it: setting it to Vietnam changed nothing. Hibernate's default `Instant` type (`TIMESTAMP_UTC`) does the work; the tests only failed when that type was overridden too. Test comment corrected |

## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now |
|---|---|
| `@DateTimeFormat` on a field with a setter | The same annotation on a `record` component; a wrong format is a normal validation error |
| `list.get(0)` | `list.getFirst()` (Java 21, sequenced collections) |
| `Timestamp` / `Date` from a JDBC call | `Instant` in entities; `LocalDateTime` for a raw UTC value in test SQL |

## Concepts explained during this task

- **A Vietnam day in UTC:** Vietnam is UTC+7, so 22/10 runs from `2026-10-21T17:00:00Z` up to `2026-10-22T17:00:00Z` (not included). That is why `to` becomes "before the next midnight".
- **History keeps its names:** a movement stores the SKU and product name as they were at that moment, so a rename doesn't rewrite the past.
- **A test should be able to fail:** the new `createdAt_isStoredInUtc_whateverTheZoneOfTheJvm` only proves something on a JVM that isn't on UTC. Overriding the setting and watching it fail showed it works, and showed which setting really matters.
