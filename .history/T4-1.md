## Goal

The third domain service: running, secured and with its tables, ready for the warehouse and stock endpoints, and for the Kafka saga in Phase 6.

## What we did, step by step

### 1. Service from the template
Pom, wrapper, `application.yml` (port 8083, `inventory_db`), Dockerfile, compose entry. Security from the start: `WebSecurityConfig` with reading for STAFF and changing for MANAGER. Nothing in the library or gateway had to change: the shared auto-configuration and the existing route were enough, which is what the T3.4 work paid for.

### 2. Migrations, one per table
- `warehouses`: unique `code`.
- `stock_levels`: one row per product and warehouse, `version`, CHECK `on_hand >= 0` and `0 <= reserved <= on_hand`. `available` is calculated, never stored.
- `stock_movements`: signed `quantity`, `reference`, indexes for the filters of T4.4.
- `stock_reservations`: one per order line, `status`.
- `processed_events`: unique `event_id`.

### 3. Copies of product data
`product_sku`, `product_name` and `reorder_level` on `stock_levels`, SKU and name on `stock_movements`. Not in the task text, but this service can't join `product_db`, the conventions say to keep a copy of what a service shows, and the low-stock filter compares in SQL. How they stay fresh is T4.3's decision.

### 4. Tests
`MigrationsTest` with plain SQL (no entities yet), `SecurityRulesTest`, `InventoryServiceApplicationTests`: 18 tests.

## Problems we hit and how we fixed them

| Problem | Fix |
|---|---|
| CHECK tests expected `DataIntegrityViolationException` | MySQL refused the rows, but Spring has no category for error 3819 and throws `UncategorizedSQLException`. The test accepts `DataAccessException` and still checks the constraint name; the conventions now say services check such rules first |

## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now |
|---|---|
| MySQL parsed `CHECK` and ignored it | MySQL 8.0.16+ enforces it |

## Concepts explained during this task

- **Calculated, not stored:** a stored `available` could disagree with `on_hand` and `reserved`.
- **Optimistic locking:** `version` lets an `UPDATE` succeed only if nobody changed the row since it was read.
- **CHECK constraints** as a last line of defence: the code gives the friendly error, the database guarantees the rule.
