## Goal

The first real screens: list, create, edit and delete products against product-service, on desktop and phone. They also set the pattern (hooks, buttons, rules) that T2.4 and later list/form pages copy.

## What we did, step by step

### 1. Full width (your option A from the T2.2 review)
- `AppLayout` no longer caps content at 1280 px; `minWidth: 0` on the content lets wide tables scroll inside their card.
- Form cards keep `maxWidth: 960`, so two form columns stay readable.

### 2. API layer
- `api/products.ts`: `getProducts`, `getProduct`, `createProduct`, `updateProduct`, `deleteProduct`.
- `api/suppliers.ts`: `getSuppliers`; `getCategoryOptions` / `getSupplierOptions` turn one page of 100 (the API's maximum) into Select options.

### 3. Shared hooks and components
- `hooks/usePagedList.ts`: list state **in the URL** (`?page=2&sort=salePrice,desc&status=ACTIVE`), loading/error state, table `onChange`, `setFilters` / `resetFilters`, `reload`. Default values stay out of the URL. A page past the end (after deleting the last row) jumps to the last page.
- `hooks/useSelectOptions.ts`: Select choices loaded once from the API.
- `hooks/useReturnTo.ts`: links to a form carry `state={ returnTo: <list URL> }`; Save/Cancel go back there.
- `components/EditButton.tsx`, `DeleteButton.tsx`: the mockup's small row buttons, icon only on phones; Delete asks with a `Popconfirm`.
- `utils/table.ts`: `sortOrderOf` (URL sort → column arrow); `toTablePagination` now takes the requested page, so the pager moves at once.
- `utils/errors.ts`: `formFieldErrors<Values>` typed for `form.setFields`.
- `constants/validation.ts`: SKU pattern, lengths, money limits, mirroring `CommonValidationUtils` and the DTO.

### 4. Pages
- **List:** search (Enter), category / supplier / status filters, Reset, backend sorting on every column (category and supplier by `category.name` / `supplier.name`), paging "21-24 of 24", load error with **Try again**.
- **Form:** one page for new and edit; two columns on desktop, one on phones; browser checks for required fields, SKU pattern, lengths, money with 2 decimals; backend `VALIDATION_FAILED` under the fields, `DUPLICATE` under SKU; success message; audit line ("Created … by …"); an unknown id shows the backend's text, a non-numeric id shows "Page not found" without a request.

### 5. Theme and texts
- Card like the mockup's `.card` (radius 14, padding 20); table header colours; no grey shading on the sorted column.
- Required-field message ("SKU is required") from `texts.ts` through `ConfigProvider`'s `validateMessages`.

### 6. Checking
- Sample catalog added through the API (5 categories, 4 suppliers, 24 products) because the database was empty.
- Headless Edge via the DevTools Protocol: paging, sorting, search, URL filters, Reset, empty submit, bad and duplicate SKU, create, edit from a filtered list and back, delete with confirmation, unknown and invalid id, phone and tablet layouts.

## Problems we hit and how we fixed them

| Problem | Fix |
|---|---|
| `form.setFields(formFieldErrors(...))` didn't compile with a typed form: field names from the backend are plain strings | `formFieldErrors<ProductRequest>(error)` with one documented cast inside |
| The sorted column was shaded grey | Table tokens `bodySortBg`, `headerSortActiveBg` |
| Build warning: vendor-antd 822 kB once Table/Form/Select are used | `chunkSizeWarningLimit: 1000` with a comment: it's cached, and splitting wouldn't shrink the total |
| Ports 5173 and 8082 already in use | Your own dev server and product-service were running; tests used them |
| First phone test opened product 1, which no longer exists (ids continue after deleted rows) | Second run with a real id |

## New compared to Java 8/11 and Spring Boot 2.x

| Java / Spring | React / TypeScript |
|---|---|
| `@RequestParam` + `Pageable` on the server | `useSearchParams()`: the same parameters, read and written in the browser |
| Session attribute "last search" | List state in the URL, `state` on a link for "return to" |
| Bean Validation on the DTO | Form `rules` for quick feedback; the backend still validates |
| `BindingResult` field errors in a Thymeleaf form | `form.setFields()` with the backend's `errors[]` |
| Generic method with a cast at the boundary | `formFieldErrors<Values>()` |

## Concepts explained during this task

- **Why the list state lives in the URL:** reload, Back, bookmarks and shared links all show the same list, and the form can send you back to it.
- **Loaders declared outside the component:** a function created inside would be a new one on every render, and the hook's effect would run again and again.
- **"Request key" instead of a loading flag:** the hook compares the last answer's key with the current URL, so it never needs to set state synchronously inside an effect.
- **`key` to reset a component:** a new `key` makes React create the search box (or the form) again with fresh initial values.
