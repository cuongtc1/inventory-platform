## Goal

Everything the saga needs before its first real event: topics, a shared message format, Spring Kafka in both services, and tests against a real broker.

## Your decisions

| Question | Choice |
|---|---|
| Where shared Kafka code lives | Topic names, envelope and publisher in `stockline-common`; payload records in each service |
| Which Kafka the tests use | Testcontainers Kafka, the same image as docker-compose |
| How topics are created | By the services at startup (`NewTopic` beans) |

## What we did, step by step

### 1. Library: `com.stockline.common.event`
- `KafkaTopics`: the five names, 3 partitions, 1 replica.
- `EventEnvelope<T>`: `eventId`, `eventType`, `occurredAt`, `payload`; `of(type, payload, clock)`.
- `EventCodec`: envelope to JSON text and back, with a typed payload.
- `EventPublisher`: wraps a payload in a new envelope and sends it with its key.
- `CommonKafkaAutoConfiguration`: the codec, the publisher and a `NewTopic` per topic, only in services with Spring Kafka.

### 2. Services
order-service and inventory-service: `spring-boot-starter-kafka`, `spring.kafka` in `application.yml` (consumer group = service name, `auto-offset-reset: earliest`), and in Docker Compose `KAFKA_BOOTSTRAP_SERVERS: kafka:29092` plus waiting for a healthy Kafka.

### 3. Tests
One Kafka container per test run, as a static field in `TestcontainersConfiguration`. `KafkaRoundTripTest` (order-service): topics exist with 3 partitions, a round trip, same key → same partition in order. `KafkaListenerTest` (inventory-service): two `@KafkaListener`s in two groups each get the event.

### 4. Docs
Conventions §6: how Kafka works in short, and the rules (shared code, JSON text, topic creation, tests).

## Problems we hit and how we fixed them

| Problem | Fix |
|---|---|
| `KafkaAdmin.NewTopics.getNewTopics()` isn't public | The topic list became a package-private method of the auto-configuration, which the test calls |
| `KafkaTemplate` closes its producer after each send, so one `MockProducer` worked once | A fresh `MockProducer` per send, the test reads all of them |
| A container per Spring context would mean several Kafka brokers per test run | One static container shared by all contexts; checked: one Kafka started per run, nothing reached `localhost:9092` |
| The local Kafka already had the five topics | Probably created by hand when T0.3 was checked; same settings (3 partitions, 1 replica), so the services leave them |

## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now |
|---|---|
| `spring-kafka` with `JsonSerializer` and type headers | Plain JSON text in String messages; Jackson 3 ignores unknown fields by default |
| `com.fasterxml.jackson` | Jackson 3: `tools.jackson.databind.json.JsonMapper`, unchecked `JacksonException` |
| Zookeeper next to Kafka | KRaft mode: Kafka manages itself |
| `@EmbeddedKafka` in a test | A real broker with Testcontainers and `@ServiceConnection` |

## Concepts explained during this task

- **Topic, partition, offset, key, consumer group, committed offset** (conventions §6).
- **Why idempotent consumers:** a message counts as done only when its offset is committed, so after a crash it can come again.
- **Why plain JSON text:** class-name headers would tie a consumer to the publisher's classes.
- **Why topics in every service:** no start order between services.
