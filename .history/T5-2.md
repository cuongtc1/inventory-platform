## What we did, step by step

### 1. The API
`/api/customers`: list (search, paging, sort), get, create, update, delete. Built like the Warehouse CRUD: `Customer`, `CustomerRequest`, `CustomerResponse`, `CustomerMapper`, `CustomerRepository`, `CustomerService`, `CustomerController`.

### 2. Rules
- The name is unique ignoring capitals: checked by the service (`409 DUPLICATE`), and by `uk_customers_name` if two requests race.
- A blank email or phone is stored as `null`.
- A customer with orders can't be deleted (`409 IN_USE`); the foreign key backs it up.
- `search` matches part of the name or the email.

### 3. Orders column
`orderCount` per customer, for a whole page in one query. Native SQL, because the `SalesOrder` entity comes with T5.3; it can become JPQL then.

### 4. Roles
`WebSecurityConfig`: `POST /api/customers` and `PUT /api/customers/*` for STAFF, placed before the `/api/**` MANAGER rule because the first match wins.

### 5. Messages
`MessageKeys` with a `customer` section, and `MessagesPropertiesTest` from inventory-service.

## Concepts explained during this task

- **Rule order in Spring Security:** the narrow rules (STAFF may POST customers) must come before the broad one (`/api/**` needs MANAGER), or the broad one decides.
- **Counting without N+1:** the order counts of a page come from one `GROUP BY` query with `IN (...)`, not one query per row. An empty page skips it, because `IN ()` is invalid SQL.
