## What we did, step by step

### 1. Entities
`StockLevel` (`@Version`, `getAvailable()`, `isLowStock()`, `copyProduct(...)`), `StockMovement` (no setters: history isn't changed), enum `MovementType`.

### 2. Reading
`GET /api/stock-levels` with `search`, `warehouseId`, `productId`, `lowStock` (`StockLevelSpecifications`), `GET /api/stock-levels/{id}`. The entity graph loads the warehouse in the same query.

### 3. Adjusting
- `StockLevelService.adjust`: refuses 0, reads the product, hands over to the adjuster. `Propagation.NOT_SUPPORTED`: no transaction during the HTTP call.
- `StockAdjuster.apply` in one transaction: warehouse, stock level (created on first use), refreshed copies, the rule, `on_hand`, the `ADJUST` movement, flush.
- `ProductClient`: `RestClient`, the user's token, 404 becomes `ResourceNotFoundException`.

### 4. Library
`InsufficientStockException`; `@Version` conflicts become `409 CONCURRENT_UPDATE` in `DataExceptionHandler`.

### 5. Cleanup from T4.2
`skuCount` moved from a native query to JPQL in `StockLevelRepository`.

## Concepts explained during this task

- **Why a separate `StockAdjuster` bean:** `@Transactional` works through a proxy, so it only applies to calls from another bean.
- **No HTTP inside a transaction:** a slow service would hold a database connection.
- **Copies pay off:** with product-service down, adjusting gives 503, but the stock list keeps working.
- **Table relationships (your question):** foreign keys exist only inside a database. `stock_levels` is the many-to-many table between products and warehouses, with a plain `product_id` across databases. `users` has no foreign keys; `created_by` holds the email as text.
