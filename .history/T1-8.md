### 2. Decisions (tech lead)
| Decision | Why |
|---|---|
| Build context = repo root, Dockerfile at `services/product-service/Dockerfile` | The image must build `libs/stockline-common` first; Docker can only copy files inside the context |
| Multi-stage: JDK build stage, JRE runtime stage | Build tools and sources stay out of the final image |
| Tests skipped in the image (`-DskipTests`) | Testcontainers needs a Docker daemon, which doesn't exist inside `docker build`; `mvnw test` runs before every commit |
| Compose profile `services` | A plain `docker compose up -d` still starts only MySQL + Kafka, so it doesn't clash with the service running from the IDE on 8082 |

### 3. Implementation (done by the coder subagent)
- **Dockerfile**
  - Build stage `eclipse-temurin:21-jdk`: copy the library, `mvnw install -DskipTests`, then copy the service and `mvnw package -DskipTests`. A BuildKit cache mount keeps `/root/.m2` between builds.
  - The jar is split with `java -Djarmode=tools -jar app.jar extract --layers --launcher`. The layer names come from the jar's `BOOT-INF/layers.idx`: `dependencies`, `spring-boot-loader`, `snapshot-dependencies` (only `stockline-common`) and `application`.
  - Runtime stage `eclipse-temurin:21-jre`: one `COPY` per layer, non-root system user `spring`, `ENV TZ=UTC`, `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=75`, `ENTRYPOINT ["java", "org.springframework.boot.loader.launch.JarLauncher"]`.
  - Before writing it, the coder checked the extract options with `help extract` and started the extracted app locally with `JarLauncher`.
- **`.dockerignore`** at the root: an allowlist (`*`, then `!libs/`, `!services/`), minus `target/`, IDE files and `.env*`.
- **Compose:** `product-service` with `profiles: ["services"]` and image `stockline/product-service:local`. It is configured by environment variables (`SERVER_PORT`, `DB_URL=jdbc:mysql://mysql:3306/product_db`, `DB_USERNAME`, `DB_PASSWORD`, `TZ`) and the port comes from `${PRODUCT_SERVICE_PORT:-8082}`. It starts only after MySQL is healthy.
- **Healthcheck:** bash `/dev/tcp` sends `GET /actuator/health` and checks for `200`. The JRE image may have neither curl nor wget, and `CMD-SHELL` would use dash, which has no `/dev/tcp`.
- **Docs:** Docker section in the service README, "Services" in the infra README, root README, `CLAUDE.md` commands, a "Docker" part in conventions section 7, and `PRODUCT_SERVICE_PORT` in `.env.example`.

## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now |
|---|---|
| `java -Djarmode=layertools -jar app.jar extract` | `java -Djarmode=tools -jar app.jar extract --layers --launcher` (Boot 3.3+) |
| Launcher `org.springframework.boot.loader.JarLauncher` | `org.springframework.boot.loader.launch.JarLauncher` (moved in Boot 3.2) |
| Downloading dependencies in every image build, or tricks with `dependency:go-offline` | BuildKit `RUN --mount=type=cache,target=/root/.m2` (BuildKit is the default builder since Docker 23) |
| `-Xmx` fixed in the image | `-XX:MaxRAMPercentage=75`: the JVM sizes its heap from the container's memory limit |

## Concepts explained during this task

- **Multi-stage build:** several `FROM`s in one Dockerfile. Only the last stage becomes the image, so the JDK, Maven and sources stay behind. Result: 172 MB of content.
- **Layers and caching:** Docker reuses a step's result if that step and every step before it are unchanged. So things that rarely change go first (dependencies, the library), things that change often go last (application classes).
- **Spring Boot layered jar:** the jar knows which files are dependencies, which are SNAPSHOT dependencies and which are your code (`layers.idx`). Extracting and copying them separately means a code change rebuilds only the small `application` layer.
- **Non-root:** if the app is compromised, the attacker isn't root inside the container.
- **Compose profiles:** services with `profiles:` start only when that profile is named; `docker compose ps` still shows them while they run.
- **Healthcheck vs. `depends_on: condition: service_healthy`:** a container can be "running" long before the app inside accepts connections; health makes "ready" visible.
- **Subagents (tried in this task):** coder, tester and code-reviewer worked as separate agents. You decided afterwards that the project doesn't need them; they were removed in the commit that marks T1.8 and T1.9 done.
