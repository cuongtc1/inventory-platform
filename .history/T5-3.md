## Goal

Take an order: a customer, a warehouse and lines, with the product data of that moment and a number people can read.

## What we did, step by step

### 1. Entities
`SalesOrder` (lines added only through `addItem`, total recalculated, `@Version`, no status setter), `SalesOrderItem` (line total calculated), `OrderStatusHistory`, `NumberSequence`; enum `OrderStatus`.

### 2. Creating
- `SalesOrderService.create` (`NOT_SUPPORTED`): cheap checks first (product twice, customer exists), then the warehouse and each product over REST, inactive products refused, total checked against DECIMAL(12,2).
- `SalesOrderCreator.create` (one transaction): number, order, lines, first history row (`→ PENDING`).
- `ProductClient`, `WarehouseClient` and one `ForwardUserToken` interceptor for the user's token.

### 3. Order numbers
`V5__create_number_sequences.sql`: a counter row per document type, `sales_order` starting at 1001. `NumberSequenceRepository.findByName` with `@Lock(PESSIMISTIC_WRITE)` (`SELECT ... FOR UPDATE`); `OrderNumberGenerator` with `Propagation.MANDATORY`.

### 4. Reading
`GET /api/sales-orders` (search in number or customer name, customer, status, newest first) and `GET /api/sales-orders/{id}` with lines. Not in the task text, but T5.5 is frontend only and needs them.

### 5. Shared code
`TextUtils.containsPattern` and `LIKE_ESCAPE` in `stockline-common`: the second copy of the LIKE escaping. inventory-service keeps its own copy until an inventory task. The customer order count became JPQL in `SalesOrderRepository`.

## New compared to Java 8/11 and Spring Boot 2.x

| Old | Now |
|---|---|
| `@Lock` rarely needed | `@Lock(LockModeType.PESSIMISTIC_WRITE)` on a Spring Data method |
| Default propagation everywhere | `Propagation.MANDATORY` for code that must run inside the caller's transaction |
| A custom validator for list elements | `List<@Valid @NotNull Item>`: errors name the line, `items[1].quantity` |
| `shutdown()` in `finally` | `try (ExecutorService pool = ...)`: `AutoCloseable` since Java 19 |
| Interceptors on `RestTemplate` | `RestClient.Builder.requestInterceptor(...)` |

## Concepts explained during this task

- **Pessimistic vs optimistic locking:** `@Version` (optimistic) detects a conflict and fails one side; the counter needs every caller to succeed, so it waits for the row lock instead.
- **Why not `MAX(order_number) + 1`:** two transactions read the same maximum at the same moment.
- **No gaps:** the counter changes in the order's transaction, so a refused order rolls its number back.
- **A test should be able to fail:** without `@Lock` the 8-thread test found duplicates; with it, none.
